## 🧭 本节定位

你的代码有没有 Bug？你不会想通过"玩家投诉"来发现。**测试不是"找 Bug"——是"证明没有 Bug"。**

## 📖 冒烟测试——硬件时代的名字，软件时代的智慧

"冒烟测试"（Smoke Test）这个名字来自电子工程时代。工程师把新设计的电路板第一次通电时——如果某个元件质量有问题，它会**冒烟**。所以"冒烟测试"的意思是：通电 → 检查 → 没有冒烟 → 基本功能 OK → 可以进行更深入的测试。

游戏行业借用了这个概念：**冒烟测试 = 启动游戏 → 玩 30 秒 → 没有闪退 → 核心循环完整 → 可以进行完整测试。** 它的价值不在于"全面"——在于"快"。游戏冒烟测试应该能在 5 分钟内跑完。

为什么需要它？因为你每次改完代码——比如"我加了一个新敌机类型"——你可能破坏了另一个完全不相关的东西（比如新敌机初始化时访问了一个被重构过的类名）。你不可能改一行代码就手动跑完整通关测试——但 5 分钟的冒烟测试是可行的。改完→冒烟→通过→push。这个循环如果成为习惯，你的 Bug 暴露率会降 80%。**这和前端开发中每次 commit 前跑 lint + 单元测试的 Guard 机制完全一致。**

## 🔍 测试金字塔——游戏版

测试领域最经典的模型是 Mike Cohn 的"测试金字塔"。游戏版本的金字塔是这样的：

**底层：单元测试（Unit Test）——最多，最快，最稳定。** 测试纯逻辑函数——不依赖任何 Cocos API、不依赖渲染、不依赖输入。用 Vitest 在 Node.js 中跑，每个测试 0.1 秒。

- ScoreCalculator：输入击杀的敌机类型，输出应得分数——期待 calcScore('small') === 10
- DamageCalculator：输入攻击力 + 护甲，输出实际伤害——期待 calcDamage(100, 20) === 80
- WaveGenerator：输入波次号，输出该波敌机配置——期待 genWave(5).boss.name === 'CrimsonStriker'（第 5 波是 Boss 关）

关键技巧：**把计算逻辑从 Component 中抽离成纯函数**。如果你的 calcScore 是在 PlayerController 的 onCollision 里内联写的——你没法单独测试它。抽成独立的 calcScore() 函数 → 可测试 → 可复用 → 干净。

**中层：集成测试（Integration Test）——数量中等，验证模块协作。** 测试多个模块之间的交互——GameManager 的状态机转换、EventBus 的事件传递、ObjectPool 的 get/put。这些需要 Cocos 运行时环境（可以在 Cocos 编辑器中跑）。

- GameManager 状态机：dispatch('start') → state 从 MENU 变为 PLAYING → UI 隐藏菜单显示游戏界面
- EventBus：emit { type: 'enemy-killed', enemyType: 'boss' } → ScoreManager 收到事件并加了 500 分
- ObjectPool：连续 get 10 个 bullet → 没有超池 → put 3 个 → 再 get 3 个 → 拿到的是刚才 put 的那 3 个

**顶层：端到端测试 / Playtest（体验测试）——最少，最慢，最"贵"，但最重要。** 完整的"真人在真机上跑完整流程"测试。Playtest 不是"找 Bug"——是**找"和预期不一致的体验"。**

## 👀 Playtest——最被忽视的最重要测试

Playtest（体验测试）和功能测试有本质区别。功能测试回答"程序对不对"，体验测试回答**"玩家懂不懂"**。

宫本茂有一个著名的"马里奥测试法则"：**"游戏的第一关应该不需要任何文字说明就能让玩家学会所有操作。"** 《超级马里奥兄弟》的 World 1-1 是这条法则的完美示范：你一开始出现在屏幕左侧（本能反应——往右走），第一个遇到的敌人是蘑菇怪（走到它面前→自然被撞死→学会"要躲开敌人"），然后出现一个"?"砖块（跳起来顶→顶出蘑菇→蘑菇自动移动→本能去碰→变大——**整个过程中没有任何弹窗告诉你"按 A 键跳、碰到蘑菇会变大"**）。

这就是 Playtest 的终极标准：**把游戏给一个完全没玩过的人，不给任何提示，看他们在前 30 秒做什么。** 如果他们卡住了——不是玩家笨，是你的设计有问题。

Playtest 的实操注意事项：不要指导——你站在旁边解释"这个是开始按钮"等于作弊。录屏 + 录表情——玩家的微表情（皱眉/张嘴/笑）比他们的口头反馈真实 10 倍。找不同类型的人——游戏玩家和非游戏玩家都要测——前者会告诉你手感好不好，后者会告诉你引导够不够。

## 🔧 动手：为飞机大战搭建测试体系

1. **单元测试（脱离 Cocos）：** 创建一个纯 TypeScript 文件——`src/game-logic/calculator.ts`。把 calcScore(enemyType: 'small'|'medium'|'large'|'boss'): number 实现为纯函数——不 import 任何 Cocos 模块。用 Vitest 写 4 个测试用例：calcScore('small') → 10，medium → 25，large → 50，boss → 500。运行 `npx vitest run`——0.1 秒通过。这一刻你就知道"我的计分逻辑是稳定的"。再加一个 calcDamage(atk, armor) → Math.max(1, atk - armor) 函数和 2 个测试（有护甲、无护甲）。
2. **集成测试（Cocos 环境）：** 在 Cocos 项目中测试 GameManager 的状态机转换。编写一个测试场景——不包含任何玩家操作，纯粹用代码驱动：`gameManager.startGame()` → 断言当前状态是 PLAYING → `gameManager.pauseGame()` → 断言是 PAUSED → `gameManager.resumeGame()` → 断言是 PLAYING → `gameManager.gameOver(score: 3200)` → 断言是 GAMEOVER + finalScore 是 3200。确认每个状态转换前后 UI 元素（开始按钮/暂停按钮/分数文本）的可见性正确。
3. **Playtest（找 2 个朋友）：** 找两个朋友——理想情况下你不需要"找游戏玩家"，就找普通朋友。把飞机大战给他们，说："帮我试玩一下。"然后——闭嘴，站到他们身后，拿手机录屏（拍屏幕）+ 录表情（拍脸）。观察：
   - 第一秒他们做了什么？有没有犹豫？有没有点错按钮？
   - 他们什么时候笑了？（= 找到爽点——加倍投入这里）
   - 他们什么时候皱眉/叹气/把手机放下了？（= 找到痛点——修复这里）
   - 他们主动说"再来一次"吗？（= 核心循环有吸引力——这是终极验证）
   把发现的 3 个最严重问题修掉。然后找另一个人再测一次——看修完之后体验是否改善。

## 🔗 课外延伸

- **World 1-1 是无字引导的教科书——至今 40 年了：** 1985 年《超级马里奥兄弟》World 1-1 的设计被游戏设计师拆解了无数次。它从"空白屏幕→右走的强制方向"、"第一个蘑菇怪的安全距离"、"第一个?砖块正好在跳跃弧线顶点"到"第一个坑正好让玩家学会'跑跳'"，每一个元素的位置都是精确计算过的。40 年过去了，手游新手引导依然在沿用这个设计思路——**不是"教你玩"，是"让你在操作中学会"。** 你的飞机大战引导同理：不要让玩家读文字——让第一个敌机从右边慢慢飘过来，玩家本能就会点射击按钮，然后看到敌机爆炸+加分，瞬间理解"射击=消灭敌人=得分"。
- **自动化 Playtest 是 2020 年代的前沿：** 大规模游戏公司（如腾讯、网易、Supercell）已经开始用 AI Agent 做 Playtest——让数千个 AI 对局自动运行，分析它们的死亡分布、耗时、放弃点。这些 AI 不需要"聪明"，只需要"不像人那样对重复劳动感到无聊"。虽然你不需要做到这个级别，但了解这个趋势——未来 5 年内 AI Playtest 会像现在的 CI 自动测试一样普及。
- **测试覆盖率不是越高越好——70% 是"收益最高"的线：** 追求 100% 测试覆盖率会花掉你大量时间在测试"无关紧要"的边缘 case 上。但核心逻辑（计分、伤害、状态机）必须 100% 覆盖——因为它们在每次游戏循环都会被调用。这个原则和前端测试一样：业务核心逻辑必须有测试，展示性 UI 组件可以依赖视觉验证。
