## 🧭 本节定位

微信小游戏不是"在微信里打开一个网页游戏"。它的运行环境、API、包体限制、分发逻辑和 Web 有本质不同。这一节把全景画给你看。

## 📖 5 亿月活的生态是怎么长出来的

2017 年 12 月 28 日，微信 iOS 6.6.1 版本更新。更新日志很平淡："新增小游戏功能"。但这条更新改变了一个产业。到 2024 年，微信小游戏月活用户超过 5 亿——相当于半个微信的用户每个月都在玩小游戏。

你可能觉得"这和我有什么关系？我就在 Cocos 里写个游戏发出去就行了。"但理解平台，和不懂平台，做出来的产品天差地别。

2022 年，《羊了个羊》在微信小游戏上爆火。它的玩法简单到荒唐——三消，但第二关难度陡增到几乎不可能通关。但它的社交裂变设计极其精妙：每次失败都会弹出"分享给朋友获得道具"。朋友点开你分享的卡片，直接进入游戏——**不需要下载，不需要注册，不需要任何步骤**。这种"点击即玩"的体验，是 App Store 和 Google Play 永远做不到的。

这就是微信小游戏的核心竞争力：**社交关系链 + 零门槛进入**。你分享一个 App Store 链接，好友要点"下载"→等安装→点"打开"→注册账号。微信小游戏只有一步：点开卡片，已经开始玩了。每一道门槛的提升，都会流失大量用户——这是产品设计的第一性原理，微信小游戏把它做到了极致。

## 🔍 微信小游戏到底"小"在哪里？——双线程模型详解

你写 Web 前端的时候，浏览器给你一个 JS 线程，你掌控一切：操作 DOM、绘制 Canvas、fetch 数据、setTimeout 定时。但微信小游戏**没有 DOM**。你是在一个专门优化的 JS 运行时里写游戏。

最核心的区别是**双线程模型**：

- **逻辑线程（Logic Thread）：** 运行你的游戏代码——update()、碰撞检测、分数计算、状态管理。这个线程运行在 JSCore（iOS）或 V8（Android）中。**它不能直接操作渲染。** 你需要通过微信提供的 JS Bridge 向渲染线程发指令。
- **渲染线程（Render Thread）：** 负责 Canvas 绘制、图片解码、文字渲染。它接收逻辑线程发来的绘制指令并执行。**它不能运行你的业务逻辑。** 它只认识"在 (x, y) 画一个 sprite"这种指令，不认识"敌机血量是多少"。

你可能会想：为什么要把一个线程拆成两个？这不是增加复杂度吗？

答案是**安全和性能**。如果游戏代码直接操作渲染，一个死循环就能让微信界面卡死——用户连微信聊天都切不回去。双线程模型下，渲染线程不受你控制，你的游戏代码崩溃了微信主界面不会受影响。另外，双线程允许微信把渲染任务放到 GPU 线程上独立执行，不和 JS 争抢 CPU。

这和 Web Worker 的设计哲学是一样的——把耗时计算丢到独立线程，主线程只负责 UI 响应。只不过微信小游戏把这个模式做成了默认架构。

## 🧱 审核、分成与规则——你必须知道的三件事

微信小游戏不是你想上架就上架的。你需要理解三件事：

**1. 审核规范。** 你的游戏提交后会经过微信审核团队的审查。审核周期 3-7 个工作日（App Store 要 2-4 周）。核心禁项：不能有赌博/色情/政治敏感内容；不能诱导分享（"分享才能继续玩"是红线）；不能有外部支付（必须走微信支付）。这和 Apple 的 App Review Guidelines 是一样的性质——平台保护用户体验的围墙。

**2. 收入分成。** 广告收入（流量主）与内购收入（虚拟支付）的分成一致：微信抽 30%，你拿 70%（月流水 50 万以内）。（以上分成以微信官方最新政策为准，本文仅为教学概述，请以官方文档核实）这和苹果 App Store 的三七分成完全一致——平台提供分发和支付基础设施，拿走渠道费。

**3. 小程序 vs 小游戏。** 它们不是一个东西。小程序是"应用"，用 WXML+WXSS 写 UI，面向工具/电商/服务场景。小游戏是"游戏"，用 Canvas 渲染，面向娱乐场景。小程序和小游戏的 API 有交集（都支持 wx.request、wx.setStorage），但各自有专属 API（小游戏有 wx.createCanvas；小程序有 wx.chooseImage、wx.scanCode。注意 wx.createInnerAudioContext 在小程序里同样可用，不是小游戏独有）。你注册账号时要选"小游戏"类目，别选错。

## 🔧 动手：成为微信小游戏平台的"业内人士"

1. **注册账号：** 去 [mp.weixin.qq.com](https://mp.weixin.qq.com) 注册一个小游戏账号。个人开发者用身份证注册就行（个人主体），不需要营业执照。注册后进入"开发管理"→"开发设置"，记下你的 AppID——后面 Cocos 构建时需要这个。
2. **读文档：** 打开微信官方开发者文档，重点读三篇：① 小游戏审核规范（搞清楚红线在哪里——比如诱导分享会被拒审）；② API 概览（浏览 wx.* 系列 API 的全景图，不需要每个都记住，但要知道"真有需要的时候去哪找"）；③ 收入分成规则（搞清楚你的收益结构——广告谁分多少、内购谁分多少）。
3. **下载微信开发者工具：** 从微信官方下载。用它打开任何一个微信小游戏示例项目（微信提供了官方 Demo），感受一下开发者工具的真机调试、Console、Network 面板。这些工具就是你以后日常开发的工作台——和你现在用 VS Code + Chrome DevTools 一样，只是换了"战场"。
4. **写一句话：** 完成上面三步后，用一个句子回答"微信小游戏和 H5 游戏的根本区别是什么？"写下来。这句话会成为你理解整个微信小游戏生态的"锚"。

## 🔗 课外延伸

- **社交竞争驱动力——微信的增长引擎：** 传统手游获取用户靠"买量"——在抖音/Facebook 投广告，花 2-5 美元买一个安装。但微信小游戏天然嵌入了社交关系链：好友排行榜、群排行榜、分享卡片。当你看到好友排在你前面，你想"再玩一局超过他"的概率远高于看到一个陌生人的广告。这叫"社交竞争驱动力"——它不是微信发明的（PSN/Xbox Live 成就系统比它早得多），但微信把它做到了零门槛。这和微信小程序的分销裂变——拼多多的"砍一刀"、瑞幸的"邀请好友免费喝"——是同一套底层逻辑：用社交关系替代广告费。
- **为什么 Cocos 是微信小游戏的"一等公民"：** 不是所有游戏引擎都能在微信小游戏里流畅运行。Unity 需要导出 WebGL 再适配，Unreal 根本不适合移动端小游戏。Cocos 引擎团队和微信团队有深度合作——Cocos Creator 的"构建微信小游戏"按钮背后，是引擎团队把 JSB 调用映射到 wx.* API、把 Canvas 2D/WebGL 适配到双线程模型、把资源加载适配到微信包管理机制的大量工作。选对引擎就是选择了"这些坑有人帮你踩过了"。
- **小游戏和快游戏的生态差异：** 除了微信小游戏，国内还有字节跳动小游戏（抖音）、快手小游戏、QQ 小游戏、百度小游戏。它们的技术架构相似（都是 JS 运行时 + Canvas），但用户画像和分发逻辑完全不同。抖音小游戏算法推荐（每个人刷到的游戏不同），微信小游戏社交流量（朋友玩啥你看到啥）。这和前端领域"一套代码、多端发布"在理论上可行，但平台差异会花掉你大量适配时间。
